# 07. UF2 (FAT16 가상 디스크 + 블록 파싱)

## 목적

호스트에 16MB FAT16 드라이브로 보이고, `.uf2` 파일을 드래그&드롭하면 슬롯에 기록한 뒤
FIRM 으로 적용하고 앱으로 점프한다.

## 대상 파일

- `src/ap/modules/uf2/{uf2.c, uf2.h, uf2_def.h, uf2_disk.c}`
- `tools/uf2/uf2conv.py`

## FAT16 가상 디스크

RAM 에는 부트섹터 / FAT / 루트디렉터리 3섹터만 두고, 나머지는 `read10` 에서 0 으로
채워 응답한다.

| LBA | 내용 |
|---|---|
| 0 | 부트섹터(BPB) |
| 1 ~ 128 | FAT#1 (LBA 1만 실제 데이터) |
| 129 ~ 256 | FAT#2 (LBA 129만 실제 데이터) |
| 257 ~ 288 | 루트 디렉터리 (LBA 257만 실제 데이터) |
| 289 | README.TXT (클러스터 2) |
| 290 ~ 32767 | 전부 0 |

총 32768 섹터 × 512B = 16MB, 클러스터당 1섹터, FAT 당 128섹터.

### 상수를 반드시 분리한다

```c
#define UF2_MAX_FW_SIZE     (FLASH_SIZE_FIRM - FLASH_SIZE_TAG)   // 447KB
#define UF2_DISK_BLOCK_NUM  32768                                 // 16MB
```

convex 는 `CFG_UF2_NUM_BLOCKS = CFG_UF2_FLASH_SIZE/512` 로 둘이 묶여 있다.
펌웨어 크기를 줄이면 가상 디스크 크기도 같이 줄어드는데, 손으로 만든 부트섹터는
총섹터 `0x8000` / FAT당 128섹터로 **하드코딩**되어 있어 불일치가 생기고
**호스트가 디스크를 못 읽는다.** 반드시 분리해야 한다.

분리 덕분에 메모리도 줄었다.

| 항목 | convex | 여기 |
|---|---|---|
| `MAX_BLOCKS` | 65636 | **1888** |
| `writtenMask` | 8.2 KB | **237 B** |
| `erase_map` | 32 B (64KB 단위) | **7 B** (8KB 단위) |

### README.TXT 는 동적 생성

`read10` 이 LBA 257(루트) 또는 289(내용)를 요청할 때마다 현재 상태로 다시 만든다.
루트 디렉터리 엔트리의 파일 크기 필드(두 번째 엔트리 오프셋 32 의 +28)를 실제 길이와
맞춰야 뒤에 NUL 이 붙거나 잘리지 않는다.

플래시에서 읽은 문자열은 NUL 종료가 보장되지 않으므로 `%.*s` 로 길이를 제한한다.

## UF2 블록 처리

```
호스트가 .uf2 복사 -> WRITE10 -> tud_msc_write10_cb -> uf2WriteBlock()
  ├─ uf2IsBlock()  매직/플래그 검증
  ├─ familyID == BOARD_UF2_FAMILY_ID (0xFFFF0003) 확인
  ├─ 새 전송이면 uf2TransferReset() + bootGetWriteSlot() 으로 슬롯 고정
  ├─ writtenMask 로 중복 블록 스킵
  ├─ uf2FlashWrite()
  │     ├─ uf2FlashEraseOnce()  8KB 섹터 비트맵, 전송당 1회
  │     └─ flashWrite()
  └─ numWritten >= numBlocks -> (complete_cb) uf2FlashComplete() -> uf2FlashFlush()
```

**`targetAddr` 는 절대 주소가 아니라 0-베이스 오프셋**이다
(`uf2conv.py --convert --base 0x0`). 실제 기록 위치는
`슬롯 베이스 + FLASH_SIZE_TAG + targetAddr` 다.

### 태그 기록 순서 (전원 손실 대응)

```
(1) boot_slot_t            (0x020)
(2) firm_tag_t.tag_crc     (0x010)
(3) firm_tag_t 첫 쿼드워드 (0x000)   <- 커밋
```

`firm_tag_t` 의 첫 16바이트가 `magic + fw_addr + fw_size + fw_crc` 라서, (3) 하나가
원자적으로 검증에 필요한 모든 값을 확정시킨다. 중간에 끊기면 TAG 매직이 없어 슬롯이
무효로 판정되고, 반대편 슬롯(현재 FIRM 의 백업본)은 온전하다.

### 소거 순서 논증

페이로드 오프셋 0 = 슬롯 베이스 + `0x400` = 그 슬롯의 섹터 0. 첫 블록이 섹터 0 을
지우면서 **옛 `firm_tag_t` 와 `boot_slot_t` 가 함께 지워진다.** 두 태그는 마지막에
그 지워진 영역에 기록되므로 재소거가 필요 없다.

### CRC 는 플래시를 다시 읽어 계산한다

블록이 순서대로 오지 않고 중복도 올 수 있으므로, 누적이 아니라 기록이 끝난 플래시를
다시 읽어 계산한다. `bootVerifySlot()` 의 계산과 정확히 같아야 한다.

## 완료 후 상태머신 (`uf2Update()`)

USB 콜백 안에서 무거운 작업을 하면 안 되므로 메인 루프에서 처리한다.

```
0: is_done_req 대기
1: 1000ms 대기 (호스트의 FAT/디렉터리 기록 + SYNCHRONIZE_CACHE 완료)
   -> usbDisconnect()   뱅크1 소거 중 USB 가 응답 못 하므로 먼저 끊는다
2: bootApplySlot(bootGetPendingSlot())
   실패 시 usbConnect() 후 상태 0 복귀 (벽돌이 되지 않는다)
3: 300ms 대기 -> bootJumpFirm()
```

`tud_msc_start_stop_cb` 의 eject 에서 **즉시 점프하지 않는다.** 이 명령의 CSW 를
호스트에 보내기 전에 USB 가 죽으면 Windows 에서 "장치 제거 오류" 가 뜬다.
`uf2RequestJump()` 로 요청만 남긴다.

`tud_msc_scsi_cb` 에서 **`SCSI_CMD_SYNCHRONIZE_CACHE_10/16 (0x35/0x91)` 을 성공 처리**
한다. tinyusb 내장 처리 목록에 없어 여기까지 내려오는데, 실패로 응답하면 Windows 에서
"지연된 쓰기 실패" 가 난다.

## 함정 / 주의사항

### `tud_msc_write10_complete_cb` 가 여러 번 불린다

실기에서 드러난 버그다. 전송이 끝난 뒤에도 호스트가 FAT/디렉터리 갱신으로 write10 을
더 보내고, 그때마다 `complete_cb` 가 다시 불린다. `numWritten >= numBlocks` 조건이
계속 참이라 `uf2FlashComplete()` 가 반복 실행되고, 이미 기록한 태그에 재기록을 시도해
실패 로그가 쏟아졌다.

```
[  ] uf2 flush slot0 size=141568 crc=0x31F2 seq=1     <- 1회차 성공
[E_] flashWrite() not blank 0x8100020                 <- 이후 3회 반복
[E_] uf2FlashFlush()
```

`is_done_req` 가이드 + 완료 후 `state->numBlocks = 0` 으로 해결했다.
(마침 `flash.c` 의 `not blank` 가드가 실제 손상을 막아준 사례이기도 하다.)

## 검증

```bash
python3 tools/uf2/uf2conv.py ../stm32h5-fw/build/stm32h5-w6300-fw.bin \
        --base 0x0 --family 0xFFFF0003 --convert --output /tmp/fw.uf2
cp /tmp/fw.uf2 /Volumes/H5BOOT/
```

**`--base 0x0` 를 반드시 명시한다.** `uf2conv.py` 의 기본 `appstartaddr` 는 `0x2000`
이라 생략하면 8KB 오프셋 구멍이 생긴다.
